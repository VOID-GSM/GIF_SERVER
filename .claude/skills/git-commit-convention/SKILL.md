# Git Commit Convention

## 메시지

```
<type>: <한국어 설명> (#<이슈번호>)
```

| type | 의미 |
|------|------|
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `refactor` | 코드 리팩토링 |
| `test` | 테스트 코드 |
| `docs` | 문서 |
| `chore` | 빌드·설정 등 자잘한 작업 |
| `init` | 프로젝트 초기화 |

- 설명은 대상과 결과를 쓴다. "수정", "변경"만 쓰지 않는다.
  - 좋음: `fix: 새 브랜치 푸시의 저장소가 404면 그 푸시만 건너뛰기 (#250)`
  - 나쁨: `fix: 버그 수정 (#250)`
- 이슈 번호는 브랜치 이름(`feat/#250-...`)에서 가져온다.
- 본문이 필요하면 한 줄 띄우고 **이유**를 쓴다. 무엇을 바꿨는지는 diff가 말한다.

## 단위

- **커밋 하나 = 관심사 하나.** 설명에 "및"이 필요하면 나눈다. 다섯 파일에 걸친 이름 변경은 여전히 커밋 하나다.
- 기능 코드와 그 테스트는 같은 커밋. 테스트만 추가하면 `test:`.
- 리팩토링과 기능 변경은 나누고, 리팩토링이 먼저.
- **의존 순서**로 커밋해 각 커밋이 컴파일되게 한다: Entity → SchemaPatchRunner → Repository → 예외 → Service → DTO → Controller → SecurityConfig → 테스트 → 문서·설정.

## 절차

- 한 단위씩 스테이징한다. **`git add -A`, `git add .` 금지.**
- 파일 일부만 커밋하려면 해당 hunk만 담은 패치를 만들어 `git apply --cached <패치>`(비대화형 환경이라 `git add -p` 불가).
- 커밋 전에 `git diff --staged`를 읽는다.
- `develop`/`main`에 직접 커밋하지 않는다.
- push된 커밋 amend 금지, force push 금지, `--no-verify` 금지.
- 이번 작업과 무관한 기존 변경, `_workspace/`, 로컬 설정은 커밋하지 않고 보고한다.

## 리뷰 반영 커밋

- **리뷰 코멘트 하나당 커밋 하나.** 답글에 해시 하나를 걸 수 있게 한다.
  - 예: `refactor: 라운드 소유권 검사를 서비스로 이동 (#271)`
- 이미 반영된 코멘트는 다시 커밋하지 않는다. 반영 여부는 답글이 아니라 **현재 코드**로 판단한다.
